# ObenseuerOS code notes

## `src/OsUguiPrototype.cs:OsUguiPrototype.Build`

`src/OsUguiPrototype.cs:OsUguiPrototype.Build` draws the desktop and opens the native Notepad prototype and Minesweeper window through the modding framework's `DesktopUi` API. It is not a replacement for the OS: the remaining desktop apps are not yet ported. Font rendering, shadows, blur, input behavior, scaling, and final appearance need a real Unity comparison. This prototype requires the framework branch that introduces `DesktopUi`.

## `src/OsPlugin.cs:OsPlugin.Awake`

`src/OsPlugin.cs:OsPlugin.Awake` registers the separate computer app only when `Debug/UguiPrototype` is enabled. The existing OS remains available for side-by-side evaluation.

## `tools/ugui-reference.py:main`

`tools/ugui-reference.py:main` captures the existing web desktop and Notepad at 1280 by 720 in GitHub CI. The screenshots are reference images only: CI has no Unity player or game assets, so it cannot render the prototype or establish visual equivalence.
- `src/OsUguiPrototype.cs:OsUguiPrototype.MakeWindow` explicitly selects the Unity UI button because the game's global button type has the same name.
- `src/OsUguiPrototype.cs:OsUguiPrototype.Icon` loads rasterized copies of the OS icon artwork embedded by CI. The sprites are cached for the session; a missing icon leaves its tile blank.
- `src/OsUguiPrototype.cs:OsUguiPrototype.Build` uses the OS desktop icon sizes, ordering, colors, and dark taskbar as an initial visual match. It remains an incomplete prototype, not an implementation of the other apps.
- `src/OsUguiPrototype.cs:PrototypeStatus.Update` reads the framework's game clock and wallet for the prototype taskbar while it is visible.
- `src/OsUguiPrototype.cs:OsUguiPrototype.Build` resolves canvas layout before reading host and desktop sizes; the game trace showed an unsized host caused a one-pixel Notepad window and a single row of icons.
- `src/OsUguiPrototype.cs:OsUguiPrototype.Build` registers desktop tiles with the framework's selectable control; Notepad and Minesweeper open on double-click while unported apps remain inactive.
- `src/OsUguiPrototype.cs:OsUguiPrototype.MakeWindow` uses the original close icon and aligns the close button with the right edge of the window title bar.
- `src/Ugui/MinesweeperGame.cs:MinesweeperGame` ports the existing Minesweeper board rules, including the safe first reveal, flags, question marks, flood reveal, chording, and win/loss state. Randomness is injected so CI can exercise deterministic boards.
- `src/Ugui/MinesweeperWindow.cs:MinesweeperWindow` presents the native board, difficulty controls, timer, and pointer interactions. Difficulty is stored separately from game saves as a Unity preference.
- `src/Ugui/NotepadWindow.cs:NotepadWindow` offers New, Open, Save, Save As, Select All, and word wrap, and asks for confirmation before discarding changes or overwriting a document. `src/OsNotepadStorage.cs:OsNotepadStorage` connects it to the OS's per-save disk and write guard. The standalone F9 prototype does not own that disk and reports that saving is unavailable. Closing the whole prototype or changing scenes can still discard unsaved text; those host-level close paths need integration before migration.
- `src/ToolkitPrototype.cs:ToolkitPrototype.Open` uses the framework's UI Toolkit overlay for a separate experimental desktop. `src/ToolkitNotepad.cs:ToolkitNotepad` connects the same OS storage to native Notepad controls when hosted by `src/OsPlugin.cs:OsPlugin.Awake`; the standalone F10 build has no storage. The framework close guard protects standalone close requests, but leaving a computer desk or changing scenes can still discard unsaved text. The interface needs in-game visual and input verification.
- `ObenseuerOS.csproj:EmbeddedResource` embeds rasterized icons when they are prepared from the SVG assets. The public build pipeline does not yet generate them, and a plain build without that preparation has no desktop icon resources.
- `src/OsNotepadStorage.cs:OsNotepadStorage.CheckSession` binds each editor to the current load generation and refuses file access while the game saves or loads. The editor must be reopened after load, new game, or return to the main menu so an old document cannot write into another session.
- `src/ToolkitMinesweeper.cs:ToolkitMinesweeper` presents the existing `MinesweeperGame` rules using UI Toolkit, including difficulty, timer, marks, chord and reset. The layout, pointer behavior, and visual parity require in-game verification.
- `src/Ugui/MinesweeperInput.cs:MinesweeperInput` tracks press and release state for the Toolkit board, so an off-cell release does not open the pressed cell and a chord does not also reveal on release.
- `src/SolitaireGame.cs:SolitaireGame` implements Klondike deal, stock cycling, legal moves, scoring and finish rules without Unity dependencies. `checks/Solitaire/Program.cs:Program.Main` exercises the rules in public CI. `src/ToolkitSolitaire.cs:ToolkitSolitaire` provides an initial Toolkit table with drag, double-click, undo and draw modes; its visuals, interaction, auto-finish and win presentation need in-game verification.
- `src/ToolkitPrototype.cs:ToolkitPrototype.Build` keeps app windows in their own layer under the taskbar. `src/ToolkitNotepad.cs:ToolkitNotepad`, `src/ToolkitMinesweeper.cs:ToolkitMinesweeper`, and `src/ToolkitSolitaire.cs:ToolkitSolitaire` use the framework's Toolkit title-bar drag and focus behavior.
- `src/ToolkitRecycle.cs:ToolkitRecycle` lists, restores, permanently deletes, and empties the existing Recycle Bin. `src/OsNotepadStorage.cs:OsNotepadStorage` applies the current session and save guards to these operations. The standalone prototype has no storage, and Unity input, appearance, and cross-app refresh still need in-game verification.
- `src/ToolkitExplorer.cs:ToolkitExplorer` provides Documents, Downloads, mod folders, navigation, search, file creation and deletion, and the existing picture gallery. `src/OsNotepadStorage.cs:OsNotepadStorage` reuses the session and save guards, and Explorer and Recycle Bin refresh each other after changes. Pictures load from the OS mod's existing `web/pictures` assets; the standalone prototype needs those assets installed alongside it to display them. Input, appearance, and image behavior need in-game verification.
- `src/ToolkitPrototype.cs:ToolkitPrototype.Update` shows the game clock and balances in the taskbar, using the same framework APIs as the earlier prototype. The Explorer shortcut opens the native Explorer window; the other taskbar shortcuts still need their corresponding UI Toolkit features.
- `src/ToolkitSettings.cs:ToolkitSettings` offers the existing wallpaper choices using `src/OsWallpaper.cs:OsWallpaper.Capture` and `src/OsGameArt.cs:OsGameArt.Ready` for game artwork, and stores the Toolkit selection in Unity preferences. The framework's appearance setting is not yet applied to the Toolkit desktop. Wallpaper appearance and input require in-game verification, and the Toolkit preference is separate from the old webview's local storage.
- `src/ToolkitStart.cs:ToolkitStart` presents the Start menu with searchable built-in app tiles and a guarded close action. `src/ToolkitPrototype.cs:ToolkitPrototype.Build` shares app launching between Start, desktop icons, and Command Prompt. Apps not yet converted are disabled, and mod-provided apps are not yet listed. Runtime layout and keyboard navigation require in-game verification.
- `src/ToolkitMail.cs:ToolkitMail` presents account signup, folders, search, selection, reading, starring, attachment actions, compose, reply, and forward through `src/MailClient.cs:MailClient.Call` and the existing scoped mail bridge. `src/MailDraft.cs:MailDrafts.ForSession` retains unsent text when the computer is reopened during the same game session and separates drafts between sessions; a new session or game restart still discards them. Session guards run before each request; actual game data, appearance, and input still require in-game verification.
- `src/ToolkitBank.cs:ToolkitBank` uses the existing bank bridge for account gates, balances, history, invoices, loan repayment, and cash-by-post orders. `src/TransactionClient.cs:TransactionClient.Write` retains transaction IDs for uncertain attempts during the current game session; the UI keeps a warning visible and requires acknowledgement before a different transaction. `src/BankQuote.cs:BankQuote.TryCreate` previews the backend's fee calculation. Transactions require confirmation. Real game effects, appearance, and input still need in-game verification; retry IDs do not survive a game restart.
- `src/ToolkitNews.cs:ToolkitNews` reads existing editions and stories through `src/NewsClient.cs:NewsClient.Call` and provides sections, related stories, figures, and static information pages. `src/NewsPhotos.cs:NewsPhotos.Pick` reads the packaged photo catalog and selects the same local images as the web edition; the existing photo credits remain in `web/photos/CREDITS.txt`. News reads can trigger the existing edition/game initialization logic. In-game appearance, asset loading, and input remain unverified.
- `src/ToolkitExchange.cs:ToolkitExchange` uses the existing exchange bridge for markets, charts, portfolio, news, previews, and buy/sell/short/cover orders. `src/TransactionClient.cs:TransactionClients.ForSession` isolates pending request IDs by app and game session; an uncertain order keeps its ID and blocks a different order until acknowledged. `src/StalExBridge.cs:StalExBridge.Result` checks the saved request record without trading, allowing a recorded order to be resolved even when a new preview is no longer allowed. `src/MarketChart.cs:MarketChart.Points` scales chart data for native drawing. Game trading, input, and visual fidelity remain unverified in-game; retry IDs do not survive restart.
- `src/Shop/ShopPurchaseIdentity.cs:ShopBridge.ResultFor` checks an existing purchase ID and its cart fingerprint without placing a new order. A missing record is inconclusive because old completed orders can be pruned; the caller must not automatically submit an uncertain purchase again. The public ShopResult check exercises the shared request and identity logic with game services stubbed.
- `src/ToolkitShop.cs:ToolkitShop` uses the existing Shop bridge for its catalog, cart, delivery, payment, and history. It uses the session-scoped `TransactionClient` to retain uncertain purchase IDs and checks `shop.result` before allowing the user to clear a matching uncertain order. The Toolkit screen, game integration, and visual parity still require in-game verification.
- `src/Wiki/WikiBridge.cs:WikiBridge.Attach` disables live wiki networking and `src/OsView.cs:OsView.Create` no longer permits live wiki frames. The offline article corpus and Toolkit reader have not yet been supplied; the current wiki cannot display articles until those are implemented.
- `src/BrowserState.cs:BrowserState` reads and writes the existing `/browser/state.json` history and bookmarks. It preserves unknown fields and refuses to overwrite malformed or unreadable saved data. `src/ToolkitBrowser.cs:ToolkitBrowser` routes available sites to Toolkit apps; other sites and the offline wiki remain unavailable pending conversion and article content.
- `src/ToolkitJobs.cs:ToolkitJobs` lists paid stations through `jobs.list` and applies using `jobs.apply`; application replies arrive through the existing mail system. `src/JobsList.cs:JobsList.Select` filters and sorts the returned jobs. In-game data, application behavior, and appearance still need verification.
- `src/ToolkitLottery.cs:ToolkitLottery` uses existing draw and scratch-card bridges and retains uncertain purchase IDs per session. `src/Lotto/LottoBridge.cs:LottoBridge.PurchaseResultFor` and `src/Lotto/LottoBridge.cs:LottoBridge.ScratchResultFor` check recorded purchases without buying. A missing record is inconclusive because history can be pruned; a new purchase after clearing an uncertain request may duplicate it. In-game purchases, payouts, shipping, and appearance need verification.
- `src/ToolkitLottery.cs:ToolkitLottery.Card` displays the packaged scratch artwork and asks the game to reveal and pay the card on the first scratch, as the web version does. `src/ScratchProgress.cs:ScratchProgress` tracks unique cleared cover cells; the cover is removed after half are cleared. Pointer behavior, artwork placement, and payout remain unverified in game.
- `src/Lotto/ScratchRecord.cs:LottoScratch.Record` refunds a wallet-card charge, or queues the existing owed-payment mechanism, if the card cannot be added. A successfully appended card stays recorded if the append reports an error after insertion. Shipped cards use the existing Shop order as evidence instead of refunding a delivery already sent.
- `src/Lotto/LottoScratch.cs:LottoScratch.Buy` recovers a matching shipped card from its Shop order before applying new-purchase limits, preserving the original price and day. `src/Lotto/LottoBridge.cs:LottoBridge.ScratchResultFor` recognizes that order as proof of a shipped purchase even when its scratch-card record is absent. Both reject reuse of its ID with different purchase details. This does not recover an order that failed before its Shop record was saved or make saves across stores atomic.
- `src/ToolkitBets.cs:ToolkitBets` uses the existing bets bridge for fixtures, quotes, placement, history, results, and standings. `src/Bets/BetBridge.cs:BetBridge.CheckExpectedOdds` rejects a changed price when the Toolkit sends reviewed odds; legacy callers can omit it. `src/Bets/BetBridge.cs:BetBridge.ResultFor` looks up retained transaction IDs without placing a bet; absence is inconclusive after history pruning, and pending IDs do not survive a game session reset. Game settlement, input, and visual parity remain unverified. `src/Bets/BetBook.cs:BetBook.Place` currently charges before recording a bet, so a recording exception after payment may leave an uncertain charge.
- `src/TerminalSession.cs:TerminalSession` implements the Command Prompt commands and history using the existing guarded disk adapter. `src/ToolkitTerminal.cs:ToolkitTerminal` presents them in a Toolkit window; app launching is limited to the apps currently converted. Runtime keyboard, layout, and game integration require in-game verification.
- `src/ToolkitChat.cs:ToolkitChat` reads saved rooms through `src/Chat/ChatGame.cs:ChatGame.Open` and sends through `src/Chat/ChatBridge.cs:ChatBridge.Send`, retaining message validation, unread counts, and simulated replies. `src/Chat/ChatHistory.cs:ChatHistory.Since` exposes all retained room messages rather than the web bridge's newest-30 response limit. The window checks the OS session before accessing chat so it cannot send into a different save. Runtime layout, input, and game integration need in-game verification.
- `.github/workflows/ugui-reference.yml:rules` runs the Minesweeper model and Notepad storage-adapter checks on GitHub's public OS repository. The adapter check uses fake game services; neither this job nor the reference screenshots compile the game integration or exercise Unity input.
- `checks/ToolkitCompile/ToolkitCompile.csproj:Compile` compiles the Toolkit windows and the framework Toolkit host against Unity 6000.0.77f1 managed assemblies downloaded by `.github/workflows/ugui-reference.yml:toolkit-compile` from Unity's official server support package. Game integration points are stubs, so this checks Unity API compatibility and C# compilation rather than game integration or rendering.
